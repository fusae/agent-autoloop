# Agent Company：一个人带多个 AI 部门

这是 `fusae/agent-autoloop` fork 新增的公司协作层。保留上游内核与 MIT 许可；公司逻辑放在 `plugins/company/`，复用原有事件、接单程序、审批卡片、重试和日志。

## 已实现

| 部门 | 职责 | 默认权限 |
|---|---|---|
| CEO（启用后） | 目标、计划审核、员工问题、负责人汇报 | 只读 |
| 产品 | 需求、范围、验收条件 | 写工作区 |
| 研发 | 实现、测试、交付说明 | 写工作区 |
| 验收 | 独立核查交付物和测试证据 | 只读 |
| 运营 | 内容与活动草稿 | 写工作区 |
| 客服 | 问题整理与回复草稿 | 写工作区 |
| 财务 | 账目核对与预算报告 | 写工作区 |
| 公司调度 | 确定性状态机，不调用模型 | 固定程序 |
| 老板 | 你通过卡片接受交付或退回 | 本人密钥 |

四条业务流程：

- `software`：产品 → 研发 → 验收 → 老板接受。
- `content`：运营 → 验收 → 老板接受。
- `support`：客服 → 验收 → 老板接受。
- `finance`：财务 → 验收 → 老板接受。

验收失败或部门报告阻塞时停止。接受交付只将任务归档，不执行上线、付款或对外发送；上游交付插件可独立使用，尚未接入公司的接受动作。

## 启动

需要 Node.js **24+**；实际业务还需要已经登录的 Codex 或 Claude Code。以下命令在本 fork 根目录运行：

```bash
npm ci
npm run company -- start "$HOME/.agent-company"
```

打开 **http://127.0.0.1:3361**，在网页里查看公司总览、任务看板、部门协作、审批和费用；点击「新建任务」填写目标与验收标准。任务详情能查看阶段、交付报告、文本交付物和历史；受阻或退回的任务可显式重新派工。

`start` 首次创建独立公司目录（默认 Codex），同时启动网页和任务引擎；目录已有则复用，不自动提交业务。Ctrl+C 停止本次启动的进程，数据保留。网页每 5 秒同步；引擎离线时仍可查看已保存任务。它只监听本机，不是公网多人服务。

点击「查看示例公司」可以体验完整界面，示例数据只保存在浏览器内存，不调用模型、不写入真实账本。命令 `npm run company:demo` 另外提供模拟部门的端到端验证。

选择 Claude 或自定义中台端口时先创建配置；如果引擎已经启动，只需运行 `web`：

```bash
npm run company -- init "$HOME/.agent-company-claude" claude 3370
npm run company -- start "$HOME/.agent-company-claude" 3371
# 已有公司引擎：只启动网页
npm run company -- web "$HOME/.agent-company" 3361
```

`init` 拒绝覆盖已存在目录，不改动 `~/.agent-autoloop`，不安装常驻服务。浏览器不接收中台密钥；接受交付仍仅代表归档。

也可另开终端提交需求：

```bash
npm run company -- submit "$HOME/.agent-company" TASK-001 examples/recipes/company/request.json
npm run company -- status "$HOME/.agent-company"
npm run company -- show "$HOME/.agent-company" TASK-001
npm run company -- history "$HOME/.agent-company" TASK-001
```

真实提交会使用本机 Agent 额度。需求 JSON 序列化后不超过 1600 字，详细需求可放工作区文件；必填 `title`、`kind`、`goal`、`acceptance`；新任务编号最多 40 位，只能用字母、数字、下划线和短横线。同编号重复提交不会派两次；变更需求使用新编号。

`status` 显示任务、审批卡片及中台费用统计。复制卡片编号，将下面的 `7` 替换成实际编号：

```bash
npm run company -- answer "$HOME/.agent-company" 7 1
```

第一项接受交付，第二项退回修改。公司审批若通过上游通道收到自由文本，按退回处理，不将模糊回答当作批准。退回后在任务目录写入修改意见，再显式重试；可指定固定请求编号，网络失败时重复同一命令仍幂等：

```bash
npm run company -- retry "$HOME/.agent-company" TASK-001 revision-1
```

QA 失败或老板退回时从前一个业务部门开始返工，之后重新验收。因环境问题被业务部门阻塞时从原部门继续。次数额度耗尽后仍保持阻塞，需要本人修改公司配置或拆分新任务。

## 经营现有 APP 或验证新业务

打开工作台左侧「业务管理」，新建业务并填写产品事实、用户、经营目标、渠道假设和官网。保存后是待启动状态；「进入业务」→「启动经营」才会产生周期工作并消耗模型额度。

网页新建业务默认启用员工职责模式：产品担任项目负责人，六个岗位分别维护责任档案。进入「员工」编辑职责、检查事项与频率；「业务动态」记录有来源的反馈或异常；「项目计划」查看员工提出的工作、期限、验收和效果跟进。每 5 分钟巡检，发现资料变化或到期复盘时派工；无变化的每日检查不调用模型，每周检查按周期运行。默认每项目同时 3 个在途任务，可在业务详情修改；默认不按每日次数暂停已批准工作，可配置公司模型额度。内部任务经 QA 后自动归档，普通手动任务仍由你确认。电脑和公司引擎须保持运行。

已有业务保持原周期模式，可在业务详情选择「启用员工职责」切换；已派发的周期任务继续执行。暂停业务只停止新派工。

在「经营数据」里填写有来源的真实指标和实际推广记录，供下一轮复盘；可通过私有 `sources.json` 配置只读数据汇总、版本和仓库资料，每小时同步；不把草稿计为已发布。当前不会自动发小红书、投广告或修改线上 APP。

## 公司资料与配置

| 路径（相对公司目录） | 用途 |
|---|---|
| `company.json` | 公司名、业务数据库位置、每任务最大派工次数及可选模型调用控制 |
| `business.db` | 长期业务、周期安排、实际指标和周期任务关联 |
| `workspace/knowledge/businesses/` | 各业务档案与指标的只读资料投影 |
| `company.db` | 任务、完整状态历史、已处理输入和待回放回执 |
| `workspace/knowledge/company.md` | 业务方向、客户、产品等共享事实；默认留空待填 |
| `workspace/handbook/` | 各部门操作规范 |
| `workspace/tasks/<编号>/` | 需求、代码、草稿、测试与交付物 |
| `hub/rules.json` | 实际生效的 Agent、权限、路由、并发配置 |
| `hub/config.json` | 中台地址和私有密钥，不提交 Git |
| `rules.company.json` | 初始规则备份，修改它不会影响已运行中台 |

所有部门默认共享工作区，员工交付工作组串行，CEO 另用只读管理工作组，部门之间通过可检查的文件和结构化报告交接。部门默认使用同一种 Agent，可在 `hub/rules.json` 逐项修改 `use`、`model`、`effort`。真实业务资料与密钥应放在仓库以外。

可以通过网页或 CLI 审批，没有打开桌面或飞书通知。接飞书时按[原有通道文档](../../../docs/plugins.md#通道插件)，使用该公司独立的 `hub` 目录和本人接收位置；不自动复制已有应用凭据。

## 保证与限制

- **路由校验**：每部门有独立的回执来源；调度器按来源、当前部门和派工编号校验，不信任报告自称的身份。
- **验收门槛**：只有 QA 报告通过、附交付物和核验依据后才向老板申请接受；程序校验结构，业务真实性仍依赖实际 QA 检查与本人验收。
- **持久化**：任务状态、历史和回执缓存在同一个 SQLite 事务内提交。进程重启后可重放相同回执；中台负责事件去重。备份应停机复制整个公司目录，包含两套数据库和密钥。
- **派工上限**：默认每任务 6 次部门派工，返工不清零；调度程序不消耗模型额度。这个限制不包含上游对失败运行的自动重试、回执修复，也不是美元硬预算。
- **费用统计**：复用中台上报的 Token 与美元费用；未上报保持未知，不估算成零。当前费用是中台总量，不是每任务账单。
- **跳数**：完整软件流程的审批在原有 8 跳上限内；CEO 模式的自动修复与新派工等待独立定时检查，保留完整跳数预算，不在原链条上重置跳数。
- **权限**：角色约束与 CLI 沙箱不是多租户安全隔离；同系统账号仍可能读到工作区外文件。正式隔离需独立系统账号或容器；本版不提供恶意 Agent 防护保证。
- **范围**：这是可运行的公司协作原型，不包含 CRM、收付款、工资、法务；营销发布需配置专用渠道入口；任务完成不等于产品已上线。

## CEO 与飞书

运行 `npm run company -- ceo "$HOME/.agent-company"` 启用 CEO；再运行 `npm run company -- feishu "$HOME/.agent-company" ou_本人编号`，重启公司服务后生效。通道使用已授权 lark-cli 机器人；启用卡片回调后，由公司通道管理该应用唯一的事件消费连接，勿另开监听。

启动业务后，CEO 先核对进展、数据入口和阶段目标，再安排员工。员工提案由 CEO 审核，问题先由 CEO 解决；无法判断才在飞书询问。按消息中的 `#编号 你的回答`（兼容旧 C 编号） 回复，答复会作为对应项目知识保存，后续员工共享。网页「CEO」显示目标、问题、决策与知识。内部任务经独立验收后由 CEO 审核，运营发布需配置固定入口，广告投放未接入；数据是否已连接以 CEO 页的数据连接为准。

持续运营会处理员工结果、有限修复无效报告、保存交付并安排效果复盘；配置系统用户服务后可在关闭网页或终端后继续。详见[持续运行与数据连接](../../../docs/company.md#持续运行与故障恢复)。

服务器常驻运行与带认证的 HTTPS 网页部署见[服务器部署](../../../docs/company.md#服务器部署)；迁移时先停本机副本，保留任务账本和飞书问答。

飞书答复只确认一次，包含问题与答复摘要；内部巡检完成不再单独通知，实际处理结果仍保留事项与正文。

飞书可直接向 CEO 提问业务进展、员工工作或阻塞原因，无需待办编号。CEO 每轮只读查询最新业务账本、职责计划、负责人答复、交付记录和带采集时间的数据汇总；最近问答用于追问，缺失资料明确标注。普通对话既能查询，也能安排内部工作、设定目标和审核员工提案；CEO 自行判断并复用现有员工、验收和复查流程，落账后反馈具体安排。缺少关键信息时追问；运营发布走成果审核及固定入口，付款和生产变更未接入，编号审批继续可用。

CEO 默认没有每日管理次数上限；相同待办最多额外复查两次，无进展时通知管理停滞，新资料自动恢复。员工列表展示当前责任和下一步，产品岗位保留项目负责人职责。

公司 CEO 模式：内部成果交 CEO 审核，退回会自动派修改任务；发布需配置工作区外的 `publishing.json` 固定渠道与适配程序。没有配置时由 CEO 处理并上报具体缺口，不会自动选择账号或虚构发布；详见公司文档“成果审核与发布”。

私有 `company.json` 可设置 `activeRoles: ["growth"]`、`inspections: false`、`ceoWake: "events"`、`dailyModelRuns: {"total":20,"ceo":4,"growth":8}`；默认保持旧行为。规则升级后重启生效，详情见[模型调用控制](../../../docs/company.md#模型调用控制)。

共用发布账号时，两个项目的私有 publishing.json 使用同一 channel；company.json 可设置 `"publishDailyLimit":1,"publishApproval":{"confirmFirst":5}`。固定程序负责本人卡片和日额度，未知结果先核实，模型不执行发布命令；缺省兼容。见[发布护栏](../../../docs/company.md#发布护栏)。
